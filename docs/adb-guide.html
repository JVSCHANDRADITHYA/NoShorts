PART 01

What adb actually is

adb is the Android Debug Bridge. Most people treat it as "the command that installs APKs", which undersells it: it is a general-purpose channel into a running Android device, and once you understand its shape the odd failure modes stop being mysterious.

Three pieces, not one

Typing adb starts a chain of three separate programs.

The client
adb.exe, the thing you actually type. It does almost nothing itself: it packages your command and sends it to the server.
The server
A background process on your PC, listening on TCP port 5037. It keeps track of every connected device and routes commands. You never start it by hand; the first adb command starts it for you.
The daemon
adbd, running on the phone. It receives commands and executes them with the privileges of the shell user.

Concept

Because the server is a separate long-lived process, it can get into a bad state that restarting your terminal will not fix. adb kill-server followed by adb start-server is the correct "turn it off and on again", and it resolves a surprising share of problems.

What it can and cannot do

adbd runs as the shell user (uid 2000) on a retail phone. That account is far more powerful than an app but well short of root.

CanCannot
Install and remove apps Read another app's private data
Change secure system settings Modify system partitions
Grant runtime permissions Become root on a retail build
Read logs, dump system state Bypass the lock screen
Inject taps and keystrokes Do anything while the phone is off

adb root exists but only works on userdebug or eng builds. On your CPH2717, a retail user build, it will refuse. That is normal and not something to fight.

PART 02

Installing it, and the PATH

adb ships in a bundle called platform-tools. You do not need Android Studio, the SDK manager, or a Google account. It is a 7 MB zip with no installer.

Google publishes the same bundle for every platform, always at a "latest" URL, so there is no version to pick:

OSURL suffix
Windowsplatform-tools-latest-windows.zip
macOSplatform-tools-latest-darwin.zip
Linuxplatform-tools-latest-linux.zip

Putting adb on the PATH

Right now you must type the full path every time. PATH is a list of folders your shell searches when you type a bare command; adding the folder makes adb work from anywhere.

Open a new terminal afterwards. A running shell reads PATH once at startup and will not see the change.

Gotcha — mixing shells on Windows

You have both PowerShell and Git Bash here, and they disagree about paths. Git Bash rewrites anything that looks like a Unix path before handing it to a Windows program, so adb shell uiautomator dump /sdcard/ui.xml becomes C:/Program Files/Git/sdcard/ui.xml and fails. This bit us during the NoShorts debugging. Two fixes: prefix the command with MSYS_NO_PATHCONV=1, or double the leading slash as //sdcard/ui.xml. In PowerShell the problem does not exist.

PART 03

Pairing: USB debugging and the RSA key

A phone will not talk to adb until you explicitly allow it. Three steps, once per device.

1. Unlock Developer options

Settings, About phone, then tap Build number seven times. A counter appears and then confirms you are a developer. This has been the ritual since 2012 and every manufacturer keeps it, though they move the screen around. On ColorOS it is under Settings, About device, Version.

2. Turn on USB debugging

Settings, System, Developer options, USB debugging.

OPPO, OnePlus, Realme and Xiaomi devices also have a separate Install via USB toggle. Without it, adb install fails while everything else works, which is a genuinely confusing failure. Some Xiaomi builds require a signed-in account before they let you flip it.

3. Accept the RSA fingerprint

Plug in the phone. A dialog shows a fingerprint and asks whether to allow debugging. Tick Always allow from this computer and accept.

Under the hood: adb generated a keypair the first time it ran, at ~/.android/adbkey and adbkey.pub. Accepting stores your public key on the phone in /data/misc/adb/adb_keys. From then on, authentication is automatic.

Gotcha — the dialog never appears

Almost always a cable problem. Many USB cables are charge-only: four wires for power, no data pair. The phone charges, the PC sees nothing, and there is no error to read. Try a different cable before anything else. If the cable is good, pull down the USB notification and switch the mode from "Charging" to File transfer. If the dialog was dismissed once, revoke and replug: Developer options, Revoke USB debugging authorisations.

PART 05

Moving apps and files

Installing

Installing over adb bypasses the Play Protect consent dialog entirely. Play Protect still scans the app and may complain afterwards, but it cannot block the install. That is why adb was the answer when sideloading NoShorts through the file manager was refused.

Gotcha — INSTALL_FAILED_UPDATE_INCOMPATIBLE

Android refuses to update an app when the new APK is signed with a different key than the installed one. This is a security guarantee, not a bug, and there is no flag to override it. You must uninstall first, which wipes the app's data. We hit this on every NoShorts release because each CI run generates a fresh debug keystore. The real fix is one stable signing key reused across builds.

PART 06

adb shell — a terminal on the phone

Android is Linux. adb shell with no arguments drops you into an interactive prompt on the device; with arguments it runs one command and returns.

Gotcha — quoting is parsed twice

Your PC shell parses the line, then the device shell parses what survives. Anything with spaces, quotes, *, > or & needs quoting for both. When in doubt, wrap the whole remote command in single quotes: adb shell 'ls /sdcard/*.xml'. Without them the * expands on your PC, against your PC's files, and the result is nonsense.

Settings, permissions, appops

This is where adb stops being convenient and starts being genuinely more capable than the UI.

settings

Android keeps configuration in three namespaces: system (per-user preferences), secure (per-user, app-protected), and global (device-wide). The shell user holds WRITE_SECURE_SETTINGS, which no ordinary app can obtain.

enabled_accessibility_services holds colon-separated entries. Writing to it overwrites the lot, silently disabling any other accessibility service the user depends on. Always read it first. We checked and found it empty before writing, which is the only reason a blind put was safe.

PART 08

logcat, and when it goes silent

Every app and system service writes to a shared ring buffer. adb logcat reads it. Unfiltered it is a firehose, so the flags matter more than the command.

A filter is TAG:PRIORITY, where priority is one of Verbose, Debug, Info, Warn, Error, Fatal, or Silent. -s NoShorts is shorthand for "silence everything, then show that tag".

Gotcha — ColorOS silently drops app logs

On your CPH2717, adb logcat -s NoShorts returns nothing at all, not even the line logged when the service starts. The service is demonstrably running. Several OEM skins, ColorOS and MIUI among them, suppress third-party app logs from the buffer unless logging is enabled in an engineering menu.

This cost us real time during debugging: an empty log looks exactly like code that never ran. If logcat is silent on a device where you know your code is executing, do not conclude the code is dead. Get your evidence another way, which is what Part 09 is for.

PART 09

Reading the screen: uiautomator

This is the command that actually solved NoShorts, and almost nobody outside test automation knows it exists.

uiautomator dump serialises the entire accessibility tree of whatever is currently on screen into XML: every view, its resource id, its class, its bounds, and whether it is on screen. It is the same data an accessibility service sees, which makes it the ground truth for anything built on one.

With no path it writes to /sdcard/window_dump.xml. A node looks like this:

bounds reads [left,top][right,bottom] in pixels. Height here is 2116 minus 120, so 1996 px on a 2392 px screen: 83% of the display, which is what a full-screen player looks like.

The diff that found the bug

Two captures, one with the Shorts player open and one after a single Back press, then compare which reel_* ids survive.

Statereel ids present
Shorts player open14, including reel_recycler, reel_watch_player, reel_player_page_container
Home feed, one Back later1 — reel_time_bar, at bounds [0,0][1080,2392]

That single surviving node was the entire bug. It was in the detection list, it outlives the player, and it reports the full screen, so it passed every "is the player showing" test we threw at it. Detection stayed true on the home feed and Back kept firing until YouTube closed.

Method

Three fixes were attempted from memory of YouTube's internals and all three failed. One capture, taken thirty seconds after finally reaching for this command, gave the answer outright. When you are reasoning about another app's UI, measure it. The tools are free and the guessing is not.

PART 10

Wireless adb

Android 11 and later can do all of this with no cable. The phone and PC must be on the same network.

Note the two different ports. Pairing uses a temporary one that changes each time; connecting uses the persistent one shown on the Wireless debugging screen.

Gotcha — this is a network service

Wireless debugging opens a port on the phone. On a home network that is a reasonable risk; on café or campus Wi-Fi, anyone who can reach the port and get you to accept a prompt has shell access to your device. Turn it off when you are done, and never leave adb tcpip mode on a phone you carry around.

Three habits worth keeping

Read before you write. Settings keys are often lists, and put replaces rather than appends. One unchecked write to enabled_accessibility_services can disable the screen reader someone actually depends on.

Treat USB debugging as a standing key to the device. An authorised computer can install apps, read logs and change secure settings without any further prompt. If you plug into a machine you do not control, revoke it afterwards.

When the phone disagrees with your mental model, dump the phone. dumpsys and uiautomator dump exist so you never have to argue from memory about what is on screen. Three failed fixes in this project were all the same mistake: reasoning about YouTube's internals from recollection instead of measuring them.
