PART 01

What you are actually running

Before any syntax, get the layers straight. Almost every beginner confusion about Java and Android is really a confusion about which layer a thing belongs to.

The JVM, and why it matters

Java source code (.java) does not compile to machine code the way C does. It compiles to bytecode (.class), an instruction set for an imaginary computer called the Java Virtual Machine. At runtime the JVM turns that bytecode into real instructions for whatever CPU it is on. That is the "write once, run anywhere" pitch.

Kotlin is a different language that compiles to the same bytecode. That single fact explains most of Kotlin's design: it can call any Java library, Java can call it back, and it inherits Java's whole ecosystem for free. Kotlin is not a layer on top of Java — it is a sibling language sharing a target.

Android does not run a standard JVM. It runs ART (Android Runtime), which takes that same bytecode and compiles it to native ARM code when your app installs. Different engine, same fuel.

Concept

You write Kotlin → the Kotlin compiler emits JVM bytecode → Android's build tools repackage it into classes.dex → ART runs it on the phone. Every language feature you are about to learn has to survive that chain, which is why some Kotlin features are "just" clever compiler tricks over plain Java constructs.

What an APK is

An .apk is a ZIP file. Rename it and open it. Inside NoShorts you will find exactly what we saw when verifying the build:

classes.dex
All your compiled Kotlin, converted to Dalvik bytecode. Ours is ~2 MB, almost all Kotlin's standard library.
AndroidManifest.xml
The app's declaration of itself: package name, components, permissions. Android reads this before running a single line of your code.
resources.arsc
Compiled resources — strings, colours, layouts — looked up by integer ID at runtime.
META-INF/
The signature. Android refuses to install an update signed by a different key than the installed version. This is exactly the wall we hit when CI generated a fresh debug key each run.

Gradle, the build system

Gradle is the thing that orchestrates: download dependencies, run the Kotlin compiler, compile resources, package, sign. You configure it in build.gradle.kts — which is itself written in Kotlin.

Gotcha

applicationId is the app's identity on the device — two apps with the same one cannot coexist. namespace is a compile-time concept only. They are usually identical, which hides the difference until the day it bites you.

PART 02

Values, types, and yes — arrays

You said you cannot build an array in Java. Let us kill that one first, then explain why you will almost never write one in Kotlin anyway.

Declaring a value

Java puts the type first. Kotlin puts a keyword first and usually infers the type.

JavaKotlinNotes
int count = 5; var count = 5 Reassignable. Kotlin infers Int.
final int MAX = 10; val MAX = 10 val = cannot be reassigned.
String s = "hi"; val s: String = "hi" Explicit type is optional.

Default to val. Reach for var only when something genuinely changes over time. In our service, backAttempts is a var because it counts up; PLAYER_ID_PREFIXES is a val because the list never changes.

The core types

Java splits types into primitives (int, long, double, boolean, char) — raw machine values — and objects (String, Integer, everything else). Kotlin presents everything as an object (Int, Long, Boolean) and quietly compiles down to primitives where it can.

String templates beat concatenation. A $ inlines a variable; ${...} inlines an expression:

Gotcha

In ShortsBlockerService.kt I deliberately wrote "Back failed " + backAttempts + " times" instead of a template. Not style — I was generating those files through shell heredocs, where a bare $ gets eaten by the shell before it reaches the file. In your own editor, always use the template form.

Arrays — the thing you asked about

An array is a fixed-length block of slots, all the same type, indexed from 0. Fixed-length is the key word: once created, the size never changes.

Gotcha

Index out of bounds is the classic crash. An array of size 5 has indices 0..4. Writing numbers[5] compiles fine and throws ArrayIndexOutOfBoundsException at runtime. The compiler cannot save you here — it does not know the index until the program runs.

Why you will rarely write an array

Fixed length is a pain. In practice you use List, which grows, and which Kotlin gives beautiful syntax for. This is what our code actually uses:

You wantKotlin
Read-only listlistOf("a", "b")
Growable listmutableListOf<String>() then .add(x)
Key → value mapmapOf("a" to 1)
Unique valuessetOf(1, 2, 3)
Length.size for all of them

The <String> part is a generic — it tells the compiler what the list holds, so masks.add(view) only accepts a View, and reading an element gives you a View back with no casting. In our service: private val masks = mutableListOf<View>().

Functions and control flow

Functions

Java writes the return type first and has no fun keyword: int add(int a, int b) { return a + b; }. Java's "returns nothing" is void; Kotlin's is Unit.

Kotlin also gives you default arguments, which is why Java's habit of writing five overloads of the same method mostly disappears:

Null, and why Kotlin exists

In Java any object reference can be null, and calling a method on null throws NullPointerException. Its inventor called it his billion-dollar mistake. Kotlin's single biggest feature is making the compiler track it.

By default a Kotlin type cannot hold null. Add ? to allow it — and then the compiler forces you to handle it.

PART 05

Classes, objects, inheritance

A class is a blueprint. An object (or instance) is one thing built from that blueprint. Prefs is a class; Prefs(this) builds one.

Those constructor parameters marked val/var become properties automatically. The Java equivalent is roughly fifteen lines of fields, a constructor, and getters. This is the single biggest reason Kotlin files are shorter.

Properties with custom behaviour

A property does not have to be storage. It can be a pair of functions wearing the costume of a variable — which is exactly how Prefs works:

Nothing is stored in the Prefs object at all. Writing prefs.blockPlayer = false looks like assigning a field, but it runs the setter, which writes to disk. Reading it runs the getter, which reads from disk. That is why the service and the settings screen always agree — they are both talking to the same file, not to a shared variable.

Concept

context has no val in front of it, so it is a constructor parameter only — usable during construction, not kept as a property. sp is a property, and private means nothing outside the class can touch it. Deliberate: callers get the typed accessors, never the raw preferences file.

Inheritance and override

Inheritance lets a class extend another, keeping its behaviour and replacing parts. This is the entire basis of Android app development: the framework defines base classes, you subclass them and fill in the blanks.

: AccessibilityService()
"extends". The parentheses call the parent's constructor. Java writes extends AccessibilityService.
override
Mandatory in Kotlin — you must state that you are replacing a parent method. Java's @Override is optional, so typos silently create a brand-new method that nothing ever calls.
super.x()
Calls the parent's version. Skip it in a lifecycle method and you will break framework bookkeeping in ways that are miserable to debug.
Concept — inversion of control

You never call onAccessibilityEvent. Android does, whenever something happens in YouTube. Your job is to be available. Nearly all Android code is callbacks the system invokes on your behalf — which is why "where does the program start?" has no clean answer here.

object and companion object

Lambdas — the one that unlocks the codebase

If one concept stops you reading ShortsBlockerService.kt, it is this. A lambda is a function you pass around like a value — a block of code handed to something else to call later.

Functions that take functions

A parameter can have a function type. (View) -> Boolean means "takes a View, returns a Boolean".

Concept — implicit return

A lambda has no return statement. Its value is whatever its last expression evaluates to. Above, the bare false and true are the return values — they look like stray words, and they are the whole control mechanism: false means "stop walking", true means "keep going".

The payoff: forEachNode knows how to walk a view tree and nothing else. hasAny, collectRects and logViewIds all reuse it with different lambdas. Write the traversal once, vary the behaviour.

Lambdas as event handlers

Read that last line: "wire up the switch with id switch_player, start it in the state currently saved in preferences, and when it changes, write the new value (it) back." The underscore in { _, checked -> } means "this parameter exists but I do not care about it".

Gotcha — the equality trap

Java's == on objects compares identity, so comparing two Strings with == is a famous bug. Kotlin flips it: == compares value (it calls equals for you, null-safely) and === compares identity. Coming from Java, you must unlearn this one.

Where our code compares rects == maskedRects, that is Kotlin == — a genuine element-by-element list comparison. It is what stops us tearing down and rebuilding the overlays on every single accessibility event.

PART 08

How Android actually works

The manifest is the app's contract

Android reads AndroidManifest.xml before executing any of your code. Nothing exists unless declared here.

android:name
The class. A leading dot means "relative to the package".
exported="false"
No other app can start it. Only the system.
permission
Whoever binds must hold this permission — in practice, only Android itself.
intent-filter
How the system discovers you. This one says "I am an accessibility service", which is what makes NoShorts appear in the Accessibility settings list.
meta-data
Points at the config XML holding the real settings.

The config that scopes our privacy claim

packageNames is the important line and the reason the README's privacy claim is honest rather than a promise: the framework refuses to deliver events from any other app. Not a filter in our code that could have a bug — a restriction enforced above us. flagReportViewIds is equally load-bearing: without it, viewIdResourceName comes back null and the entire detection strategy silently stops working.

Resources and the R class

Anything not code — strings, layouts, colours, icons — lives in res/. At build time Android generates a class called R holding an integer constant for every resource.

@+id/ means "create this ID"; @string/ means "look this one up". Keeping text in strings.xml is not bureaucracy — it is what makes translation possible, and it is why getString(R.string.stats_blocked, count) can substitute %1$d for you.

The main thread

Android draws everything on one thread. Block it and the UI freezes; block it for ~5 seconds and the system kills you. Your accessibility callbacks arrive on it.

That is why forEachNode is capped at MAX_NODES = 2500: a runaway walk of a huge view tree would stall the phone. And it is why delayed work goes through a Handler:

Looper.getMainLooper() is the main thread's message queue. postDelayed puts a task on it with a timestamp. There is no sleep anywhere in Android UI code — you schedule and return.

Concept — Runnable

escapeCheck is an object : Runnable — an anonymous class created inline, implementing the one-method interface Runnable. Written as an object rather than a lambda because it needs to re-post itself (handler.postDelayed(this, ...)), and a lambda has no name to refer to.

Everything so far, assembled. The app is five Kotlin files and about 1,000 lines total.

Detection

We cannot see YouTube's code. What we can see is the accessibility tree — the same structure a screen reader uses. Every view in it may carry a viewIdResourceName like com.google.android.youtube:id/reel_recycler. YouTube's Shorts views are internally called "reels", and that naming is the hook the whole app hangs on.

substringAfterLast('/') turns the full id into just reel_recycler. prefixes.any { ... } is a standard-library function taking a lambda: "is this true for at least one element?" Prefix matching rather than exact matching is deliberate — YouTube renames leaf views between releases far more often than it renames the whole reel_* family.

The event handler

Read it as a sequence of guards, each cheaply rejecting work before the expensive tree walk. This method runs many times per second while you scroll YouTube, so ordering matters.

The escape

This is the part we have already had to fix once, and the part still misbehaving.

performGlobalAction(GLOBAL_ACTION_BACK) is the only real power an accessibility service has here — it presses the same Back button you would. It cannot reach into YouTube; it can only drive the device.

The escaping flag is a state machine, and it exists because the first version did not have one. That version re-fired Back on every matching event with only a 350 ms debounce, and since YouTube keeps reel views in the tree throughout its exit animation, press two popped the screen behind Shorts and press three triggered the "Back isn't working" path straight to HOME. Hence: press once, wait, look again.

The overlays

An accessibility service cannot hide another app's views. So to remove Shorts shelves from the feed we draw our own black windows on top of them, positioned using the bounds the tree reports.

or here is not boolean "or" — it is bitwise or, combining flags into one integer. Each flag is a distinct bit; combining them sets several bits at once. Java writes this as |.

FLAG_NOT_TOUCHABLE is the design decision in the whole feature: touches pass straight through the mask, so the feed still scrolls normally underneath. An opaque, touchable overlay would hide the shelf and trap your finger.

Gotcha — the watchdog

Because packageNames restricts us to YouTube, we stop receiving events the moment you leave it — and our overlays would hang on screen forever. maskWatchdog re-posts itself every 800 ms, checks whether YouTube is still foreground, and tears the masks down when it is not. Every drawn overlay needs an owner responsible for removing it.

PART 10

The bug that is still in there

Real code, real defect, still unfixed at the time of writing. Reported symptom: opening Shorts closes the Short, then backs out of YouTube, then minimises it. The state machine above was supposed to fix that and did not.

The prime suspect

collectRects checks isVisibleToUser. hasAny does not.

Android's bottom-navigation tabs are typically backed by fragments that stay alive after you leave them. If YouTube keeps the Shorts fragment in the tree once you are back on the Home tab, then hasAny keeps returning true for views that are no longer on screen. The service concludes it is still in Shorts, presses Back again, pops YouTube's own screens, and eventually walks the user out of the app — with no HOME action ever fired, which matches the empty log exactly.

The fix to try

Require the match to be visible and large. The full-screen Shorts player fills the display; a cached off-screen fragment does not.

return@forEachNode false is a labelled return: plain return inside a lambda would try to exit the enclosing function, so Kotlin makes you name which one you mean.

How to confirm it before writing code

Do not guess — including when I guess. Get the ground truth:

  1. In NoShorts, turn off "Close the Shorts player" so it cannot eject you mid-capture.
  2. Open YouTube → Shorts, leave it on screen.
  3. adb shell uiautomator dump /sdcard/ui.xml then adb pull /sdcard/ui.xml.
  4. Press Back to the Home feed and dump again.
  5. Diff the two for reel_ ids. If they appear in both, the theory is confirmed.

That is the actual job: form a hypothesis, find the cheapest observation that could falsify it, then change one thing. The Kotlin is the easy part.
